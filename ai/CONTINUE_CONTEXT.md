# DAODES — Continue AI Engine Context

## 1. Назначение проекта

DAODES — проект на Laravel 11, использующий PHP 8.2+ и локальные модели Ollama для разработки, анализа кода, работы с архитектурой и управления графом знаний.

Основные цели AI Engine:

- Анализ существующего кода и архитектуры.
- Помощь в разработке и сопровождении Laravel-приложения.
- Сохранение архитектурной целостности проекта.
- Работа с базой знаний DAODES.
- Поиск связей между компонентами и зависимостями.
- Поддержка безопасного изменения существующих реализаций.
- Снижение дублирования кода и архитектурных ошибок.

ИИ является инструментом разработки. Он не должен самостоятельно изменять архитектуру, удалять данные или выполнять необратимые операции без необходимых оснований и согласования.

## 8. Правила работы с графом знаний

Основной граф знаний:

`ai/graph/living_graph.json`

Граф используется для хранения структурированных знаний DAODES и связей между элементами системы.

При работе с графом:

- Сначала изучай существующую структуру JSON.
- Определяй обязательные поля и соглашения идентификации узлов.
- Сохраняй существующие идентификаторы.
- Сохраняй связи и метаданные, не относящиеся к задаче.
- Не удаляй узлы без обоснования.
- Не удаляй связи без проверки их использования.
- Не заменяй весь граф упрощённым примером.
- Проверяй корректность JSON перед записью.
- Перед значительными структурными изменениями создавай резервную копию в разрешённой директории проекта.

Обновляй граф, если изменения действительно затрагивают знания, архитектуру, компоненты или связи, представленные в графе.

Обычная правка PHP не требует автоматического изменения графа.

Не добавляй неподтверждённые сведения в качестве фактов.

Если информация является предположением, явно обозначай её как предположение, а не как подтверждённый факт.

## 9. Правила разработки

Перед изменением кода:

1. Изучи исходный файл.
2. Изучи связанные классы и вызовы.
3. Определи влияние изменения на существующую функциональность.
4. Проверь используемые зависимости.
5. Определи минимальный необходимый набор изменений.
6. Укажи файлы, которые планируется изменить.

Во время разработки:

- Используй существующие архитектурные соглашения.
- Соблюдай PSR-12.
- Используй типизацию аргументов и возвращаемых значений.
- Применяй PHPDoc там, где он добавляет полезную информацию.
- Не дублируй существующую бизнес-логику.
- Не заменяй рабочие реализации заглушками.
- Не удаляй существующие функции без согласования.
- Учитывай обработку ошибок и журналирование.
- Сохраняй обратную совместимость, если задача не требует обратного.
- Не изменяй маршруты и публичные контракты без необходимости.

При работе с Blade проверяй синтаксис директив и сбалансированность выражений `{{ }}`, `@if`, `@foreach` и `@php`.

При работе с JavaScript учитывай взаимодействие с Blade и корректную передачу данных.

## 10. Безопасность

Не раскрывай секреты из `.env`, приватные ключи, пароли, токены и другие конфиденциальные данные.

Не добавляй секреты непосредственно в исходный код.

Проверяй:

- Авторизацию пользователя.
- Принадлежность данных пользователю.
- Валидацию пользовательского ввода.
- Права доступа.
- Безопасность API.
- Защиту от CSRF и XSS.
- Безопасность операций с базой данных.
- Корректную обработку исключений.

Не отключай механизмы безопасности ради обхода ошибок.

Не выполняй массовое удаление файлов, очистку данных, сброс базы или другие необратимые действия без явного разрешения.

Не запускай миграции автоматически без согласования.

Не изменяй критичные конфигурационные файлы без предварительного изучения их содержимого.

## 11. Работа с файлами

При создании или исправлении файла предоставляй его полное содержимое.

Для каждого файла указывай точный путь.

Не заменяй код многоточиями.

Не пропускай импорты, методы, существующие функции и необходимую логику.

Если исходный файл недоступен, не выдумывай его содержимое. Запроси исходник или укажи точное место необходимых изменений.

Не утверждай, что файл был изменён, сохранён или создан, если соответствующее действие не выполнялось.

## 12. Тестирование и проверка

После изменений проверяй результат доступными средствами.

Для PHP используй:

`php -l путь/к/файлу.php`

Для JSON используй:

`php -r 'json_decode(file_get_contents($argv[1]), true, 512, JSON_THROW_ON_ERROR);' путь/к/файлу.json`

Для Laravel-тестов используй существующую конфигурацию PHPUnit или Pest:

`php artisan test`

При необходимости проверяй маршруты:

`php artisan route:list`

Проверяй только те части системы, которые относятся к задаче, но учитывай возможные побочные эффекты.

Не запускай потенциально разрушающие команды ради проверки.

Не утверждай об успешном тестировании, если команды фактически не запускались.

Если проверка невозможна, указывай причину.
